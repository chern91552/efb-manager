# EFB Manager（Linux，v0.4.0）

独立运行的本机 Web 管理器，接管一个官方 `efb-wechat-slave` 实例。

支持主动登录、主动退出、二维码刷新、跨重启的微信会话计时、EFB 启动/停止/重启、连接健康状态以及最近 250 行日志。主动退出后不自动重新登录。页面关闭或刷新不影响计时。

新增消息记录页：左侧会话列表，右侧按时间查看消息；支持会话名称搜索、文字正文搜索、消息类型筛选、自动更新和加载更早记录。查看更早记录时暂停自动更新，可点击“回到最新”恢复。桌面使用侧栏，手机窄屏改为上下布局。

## 快速部署（已有 EFB 的 Linux 主机）

前提：已有正常工作的 EFB、官方 `efb-wechat-slave` 和 Telegram 主端配置，Python 3.9+。管理器需与 EFB 使用同一个 Linux 用户、Python 解释器和配置目录；虚拟环境不是必需条件。**当前版本尚未完成真实 Linux 微信账号扫码与收发验收。**

先停止原先运行的 EFB，避免同一个 profile 被两个进程同时使用。如果原 EFB 是系统安装，可直接从源码运行，不需要新建虚拟环境，也不需要向系统 Python 安装管理器。以下 `python3` 必须指向原 EFB 使用的解释器（如有不同，请替换为其绝对路径）：

```bash
git clone https://github.com/chern91552/efb-manager.git
cd efb-manager
python3 -m efb_manager.server --profile default --port 8765
```

原 EFB 已使用虚拟环境时，也可以激活原环境后运行上述源码命令，或执行 `python -m pip install .` 安装管理器。不要为了管理器迁移现有 EFB。

在同一台 Linux 主机的另一个终端读取管理口令：

```bash
cat ~/.local/state/efb-manager/access-token
```

本机浏览器打开 [http://127.0.0.1:8765](http://127.0.0.1:8765)，输入口令，管理器启动后会自动启动 EFB。缓存有效时直接恢复登录；缓存缺失、失效或读取失败时会暂停，点击“扫码登录”后才显示二维码，再用手机微信扫码确认。

远程 Linux 服务器：在自己的电脑上执行 SSH 转发，保持该终端连接，再访问上面的本机地址：

```bash
ssh -N -L 8765:127.0.0.1:8765 YOUR_USER@YOUR_SERVER
```

使用 SSH 转发无需开放服务器的 8765 公网端口。管理器监听成功后自动尝试启动一次 EFB，并恢复微信缓存会话；不需要先打开网页。使用 `--no-auto-start` 可改为手动启动。主动停止 EFB 后不会自动拉起，子进程退出后也不会循环重试。

如果希望直接通过服务器 IP 访问，启动命令加上 `--host 0.0.0.0`，例如 `python3 -m efb_manager.server --host 0.0.0.0 --port 8765`，然后访问 `http://服务器IP:8765`。同时需要在服务器防火墙及云平台入站规则中允许 TCP 8765。管理口令验证仍然启用；公网长期使用建议通过 HTTPS 访问。

## 微信登录到期提醒

进入 **设置 → 微信登录到期提醒**，开启提醒，填写登录后多久提醒并选择“小时”或“天”（例如 `29` 天，即 `696` 小时），保存即可。默认关闭，默认时长为 24 小时，支持 0.01–8760 小时（最多 365 天）。配置按 profile 保存于管理器 state 目录，跨管理器重启保留，约 5 秒内生效，无需重启 EFB。

当前及上次会话时长显示为“29天 3小时 12分 5秒”。在同一设置区的“自定义提醒内容”中填写要发送的文字（最多 500 字，可换行），保存后按原文发送。留空使用默认提醒，旧配置自动兼容。修改内容不会重置计时或让已经发送过的提醒重复发送。

管理器按持久保存的**当前微信会话年龄**计时，达到阈值且微信在线时，通过当前登录账号发送到**微信文件传输助手**。消息说明达到配置时长并建议检查或重新登录，不会自动退出微信，也不代表微信服务器已判定会话失效。

- 同一 `wxpy.pkl` 会话恢复时继续计时，扫码重新认证才重置。计时包含停机期间经过的时间。正式提醒的尝试状态也保留，重启不会对同一会话重复提醒。
- 离线、认证过程中不发送；关闭网页不影响后台检测。
- 在线时启用或缩短时长，若已经达到阈值且本次尚未提醒，将在下次检查时发送。
- 微信提醒发送成功后，使用返回的消息 ID 向 Telegram 主端提交同一条文本，并通过现有归档流程记录到文件传输助手会话（发出方向）。微信回传同一 ID 时去重，不会再次向微信发送。同步失败会单独提示，不会将微信发送成功误报成微信失败。
- Telegram 的会话绑定、自己发送消息过滤、中间件及网络状态仍影响实际转发；文件传输助手归档遵循私聊保存开关。此更新不补录此前的提醒。
- 每次登录最多尝试发送一次，修改设置或关闭再开启不会重复提醒。发送异常可能是服务端已收到但响应丢失，因此不自动重发；设置页和运行日志会提示失败或结果不确定，请检查文件传输助手。
- 该提醒独立于微信从端的 `_save_login_time` / `_sent_reminders`，不依赖从端的登录提醒实现；已有其他提醒功能不会被本功能自动关闭。

源码部署更新：在仓库目录执行 `git pull --ff-only`，再重启管理器服务，例如 `sudo systemctl restart efb-manager`。若通过 pip 安装，请在原 EFB Python 环境重新安装更新的项目。重启管理器会停止其 EFB 子进程，之后会自动启动 EFB 并恢复微信缓存，失败时在页面点击“扫码登录”，再配置提醒。可用 `0.01` 小时（36 秒）验证，完成后改为所需时长。

## 跨重启的会话计时

v0.4.0 起，同一个微信 Web 会话从 `wxpy.pkl` 恢复时，保留首次记录时间；重新扫码认证时重置。即使缓存文件因保存同步状态而被重写，也不会仅根据文件修改时间误判为新登录。管理器仅保存会话身份的 SHA-256 指纹、时间和提醒尝试状态，不复制 Cookie 或登录票据。

时间显示为“29天 3小时 12分 5秒”，反映会话年龄，包含停机经过的时间，不是所有在线时间的累加。29 天提醒不再因更新或重启不断归零。正式提醒尝试前先落盘，避免重启后重复发送。

**首次升级时无法推算旧缓存最初登录时间**，将从本版本首次观察到有效会话时开始记录，并显示“首次记录时间”。之后重启可沿用；重新扫码后显示实际记录的登录时间。请保留 state 目录内对应 profile 的 `.session.json`；若保存失败，页面会提示本次只能使用内存计时。

## Telegram 转发补偿与健康状态

首页分别显示微信同步/最近消息、Telegram API 请求、Manager 归档的状态和最近成功时间。归档按规则跳过时会显示“已跳过”；长期没有同步确认时显示“近期未确认”，不把没有新消息当成连接成功。Telegram 后续查询恢复正常时，如果本进程仍有失败或结果不确定的转发，会继续显示“有转发未完成”（最多跟踪最近 4096 条未完成消息）；API 可用不会抹掉这一提示。进程重启后该计数重新统计，已归档的历史结果仍保留。健康状态来自管理器观察到的调用，不是手机已读回执。

对当前使用的 **python-telegram-bot 13 系列 / ETM `SlaveMessageProcessor`** 自动适配单次 Bot API 请求：

- `getChat` 等只读请求失败，以及明确发生在建立连接前的发送失败，自动等待 1、2、4 秒重试，最多额外 3 次。复用原请求，不把整条已经部分发送的消息重新跑一遍。
- 发送后断开、读取响应超时等不能确定是否送达的情况，标记“结果不确定”，停止自动重发。API 明确拒绝的请求不作网络重试；原主端的限流机制仍负责处理限流。
- 消息记录区分“请求重试后成功”“安全重试已耗尽”“发送结果不确定”；运行日志保存重试与恢复结果，健康区显示累计重试和不确定次数。
- 重试在当前进程内执行，不提供跨重启持久补发队列，也不会自动补发升级前失败的历史消息。主端自行异步排队的请求可被重试和监测，但无法可靠回写到原归档时仅显示“已交给主端，未观察到发送请求”。

不匹配上述主端版本时显示“暂不支持检测”，不强行修改其网络实现。实际 Telegram 消息仍受会话绑定、过滤、中间件和服务端权限影响。

## 测试提醒与会话归档黑名单

在“设置 → 微信登录到期提醒”先保存自定义内容，再点击**发送测试提醒**。微信在线且 EFB 初始化完成时，立即向文件传输助手发送带“测试提醒”前缀的消息，并提交 Telegram 转发与归档。提醒总开关关闭时也能测试；不修改正式计时和正式提醒次数，每 30 秒最多一次。页面显示发送或同步结果，Telegram 的实际请求结果可结合健康区和消息记录查看。

在“设置 → 会话归档黑名单”选择已有记录的用户或群，或填入准确的 `["blueset.wechat","会话 UID"]`，加入后停止保存该会话的新消息。也可长按“微信管理”打开消息记录，右键会话选择“不再归档此会话”。黑名单按 profile 隔离并跨重启保存；已有记录不删除，微信与 Telegram 转发继续。点击“恢复归档”后仅保存后续经过的新消息，不自动补录屏蔽期间记录。

## 隐藏消息记录入口

消息记录不再出现在导航菜单、首页快捷入口和首页统计卡片中。**按住导航里的“微信管理”约 1 秒**打开消息记录，鼠标和触屏均支持；普通点击仍进入微信管理。拖动、移出或取消按压不会打开。键盘聚焦此入口后也可长按 Enter 或空格打开。

刷新页面后恢复隐藏状态，需要再次长按。此功能只隐藏界面入口，不改变消息归档和管理口令验证，也不是额外的访问权限控制。

## 删除本地消息记录

打开隐藏的消息记录页后，在左侧会话上**右键 → 删除此会话全部记录**，或在某条消息上**右键 → 删除这条记录**，确认后删除。部分触屏浏览器可通过长按调出菜单。

仅删除当前 profile 的 Manager 本地归档，不会撤回微信/Telegram 消息，不影响绑定或后续新消息归档。删除不可恢复；正在转发的消息完成状态更新不会把已删除记录重新写回来。数据库文件大小不保证立即缩小。

## 消息分类与容量上限

在“设置 → 消息保存设置”中，可独立开启或关闭私聊、群聊、公众号消息的归档。默认保存私聊和群聊，不保存公众号消息；关闭只影响新归档，不影响微信或 Telegram 转发，也不会按类别删除已有记录。旧版本已经保存的记录不会重新识别为公众号。

消息库容量上限默认 100 MiB，可设置 1 到 10240 MiB。超限后后台从归档时间最早的记录开始分批删除，通常清理至上限约 85%，并压缩数据库、截断 WAL，实际回收空间。主数据库和 WAL/SHM 一并计入使用量；清理每约 2 秒检查一次，写入和压缩过程中可能短暂超限，数据库繁忙时会自动重试。单条记录本身大于上限时也可能被清理。

页面显示当前磁盘占用及累计清理条数。该上限作用于同一 state 目录内的整个消息库，包含其他 profile 的记录；不限制原 EFB 的媒体缓存、运行日志或备份。缩小上限会触发自动清理，删除的历史不可恢复。设置即时生效并跨重启保存，无需重启 EFB。

## 自定义管理口令

登录后，进入“设置 → 修改管理口令”，填写当前口令、新口令和确认口令即可。支持 8 到 256 个字符，不能包含控制字符或首尾空白。保存后立即生效，当前浏览器保持登录，其他浏览器或设备的旧登录会话失效；EFB 和微信会话继续运行。

首次部署或忘记口令时，也可以在项目目录使用原 EFB 的 Python 交互设置（将 `python3` 替换为原解释器路径）：

```bash
python3 -m efb_manager.server --set-password
```

命令会隐藏输入、要求确认两次，设置完成后退出，不启动 EFB。若管理器服务正在运行，命令行设置后需要 `sudo systemctl restart efb-manager` 生效；该重启会停止其 EFB 子进程，之后需在页面重新启动。已有口令文件继续兼容，不会因更新自动重置。

口令仍保存于实际 `--state-dir` 下的 `access-token` 文件，Linux 下仅运行用户可读写。修改口令和服务启动必须使用相同用户与数据目录；未自定义数据目录时默认使用 `~/.local/state/efb-manager`。不要把真实口令写进命令参数、服务文件或 Git 仓库。

## 消息保留规则

- `Text` 消息保存完整文字正文，文字中的网址正常保留。
- 图片、表情、语音、视频、文件、链接卡片、位置等只保存 `[图片]`、`[表情]` 等类型占位符。未知类型显示 `[其他消息]`。不保存其说明文字、文件名、链接、缩略图或附件内容。
- 所有记录保留会话名称、发送者、收发方向、EFB 消息 ID 和归档时间；归档时间是管理器观察到消息的时间，不是手机原始发送时间。
- 数据库位于 `~/.local/state/efb-manager/messages.sqlite3`，可通过 `--state-dir` 修改。不同 EFB profile 的记录隔离，同一 profile 内按通道与会话 ID 区分。该版本不按微信登录身份创建独立档案，若需要换号并隔离历史，请使用不同 profile。
- 管理器归档模块不会打开、复制或下载媒体文件；原 EFB/微信从端为了 Telegram 转发而进行的媒体下载仍按上游行为执行。
- 记录从接入后开始，只覆盖经过 EFB 消息分发入口的微信消息，不读取手机数据库、不导入已有历史，也不保证补回停机期间的消息。
- 消息库在 EFB 停止、管理器重启后仍保留。不包含历史撤回/编辑操作的完整审计轨迹，现有消息 ID 重复时更新该条记录。
- 归档在中间件处理前提取，因此保留的是 EFB 分发入口处的文字。消息可能随后被改写、过滤或转发失败；界面的处理结果来自 EFB 调用返回，不代表微信或 Telegram 的已读回执。
- 当前不提供网页发消息、附件下载和中间件管理；支持按容量自动清理，以及手动删除单条或整个会话的本地记录。

备份时请先停止管理器，再备份整个 state 目录（SQLite WAL 文件也可能存在）。口令和聊天记录均在本机保存，目录应仅由运行用户访问。演示截图中的会话与记录是模拟数据，不会随安装包写入你的数据库。

## 安装到现有 EFB 环境

必须使用已经能运行 EFB 的同一个 Python 解释器、Linux 用户、HOME 和配置目录。原来未使用虚拟环境时，无需创建虚拟环境。管理器支持 Python 3.9+；不要为了管理器直接升级现有 EFB 的依赖。先记录版本并备份现有 profile。当前未在真实 Linux 微信账号上联调。

在解压后的项目目录可以直接运行源码（替换为原 EFB 解释器的实际路径）：

```bash
/path/to/python3 -m efb_manager.server --profile default
```

先停止原先运行的 EFB 进程或服务，避免两个实例同时操作同一个 profile。本管理器只控制自己启动的 EFB，不接管外部已运行进程。管理器启动后自动启动 EFB，并先恢复 `wxpy.pkl`；恢复失败时暂停认证，等待点击“扫码登录”。首次认证期间 EFB 可能尚未完成其他通道初始化。

首次启动生成随机管理口令，读取：

```bash
cat ~/.local/state/efb-manager/access-token
```

本机浏览器打开 `http://127.0.0.1:8765`，输入口令。不要把口令放在网址中。

如果 EFB 在远程服务器，通过 SSH 转发访问：

```bash
ssh -L 8765:127.0.0.1:8765 YOUR_USER@YOUR_SERVER
```

然后在电脑浏览器打开 `http://127.0.0.1:8765`。默认绑定回环地址；可使用 `--host 0.0.0.0` 启用服务器 IP 直连。日志可能含聊天内容，请只在自己的设备访问。

## 开机运行

源码运行时使用 `deploy/efb-manager-source.service.example`；已安装管理器时使用 `deploy/efb-manager.service.example`。编辑用户、工作目录和 Python 或管理器的绝对路径，按现有部署补充 `EFB_DATA_PATH` 等环境变量；然后保存为 `/etc/systemd/system/efb-manager.service`：

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now efb-manager
sudo journalctl -u efb-manager -n 50
```

管理器就绪后自动启动 EFB，并先恢复微信缓存；恢复失败后才需要在页面点击“扫码登录”。服务用户必须和原 EFB 用户一致，口令也在该用户 HOME 下。

## 行为与限制

- 只退出 EFB 的微信 Web 会话，不退出手机微信。主动退出或掉线后页面不再显示在线；下次恢复相同缓存时保留会话起点，重新扫码认证后重置。
- 会话起点在认证及从端基础设置成功后记录，缓存恢复沿用原记录；首次生成二维码不算登录成功。暂时断网但从端未报告退出时，界面仍可能显示原状态；这不是微信服务器在线状态的独立探测器。
- 管理器重启会停止并重新启动其 EFB 子进程；会话起点和正式提醒尝试状态按 profile 保存在 state 目录，缓存恢复可继续计时。上次退出时长仍只保留在内存。页面连接中断会显示状态未知。
- 登录过程中需要取消时，使用“停止 EFB”。尚未提供独立取消认证按钮。
- 使用安装时找到的 `ehforwarderbot` console entry point，保留 profile 参数；在子进程中适配官方 WeChatChannel 的认证、二维码和退出回调，不改动 site-packages 源文件。未来上游接口变化需要重新验证。
- 当前只支持一个微信实例。中间件管理、通用配置编辑和累计所有登录历史未包含在本版。
- 若手机本身无法登录微信网页版，管理器不能改变该限制。

## 扫码登录与缓存恢复

管理器启动时自动启动 EFB；手动点击“启动 EFB”或“重启 EFB”也一样，先读取 `wxpy.pkl` 恢复会话。成功则继续初始化；失败或没有缓存时暂停，等待用户点击“扫码登录”。等待期间不会主动获取二维码或推送手机快捷确认，可通过“停止 EFB”取消。

“扫码登录”继续当前等待中的认证，或在离线状态发起新二维码登录；普通“登录微信”先尝试缓存恢复。不会删除缓存文件，认证成功后仍由从端保存新会话。在线时需先退出微信再扫码。二维码和认证协议沿用已安装的微信从端。

## 登录协议与旧兼容适配

v0.3.5 默认保留已安装微信从端的原始登录协议，不改写二维码请求参数、认证请求头或认证字段。此前 v0.3.2–v0.3.4 自动启用的 UOS 适配可能与已有可用环境不兼容，现改为仅在显式设置 `EFB_MANAGER_LEGACY_UOS=1` 时启用，且仍限定未包含新请求头的 2.0.7。已有原服务能登录的环境请保持默认。

v0.3.10 起，启动 EFB 自动恢复缓存会话；普通“登录微信”也只先尝试缓存。缓存恢复失败（含缺失或读取异常）会暂停认证，不自动推送手机确认或获取二维码。页面显示“缓存恢复失败，等待点击扫码登录”，点击“扫码登录”后才继续，二维码参数与后续认证仍由已安装从端处理。等待期间可停止或重启 EFB；恢复失败不会标记在线。网页二维码和登录计时继续保留。

源码部署更新后重启管理器，日志应显示“使用已安装微信从端的原始登录协议。”。原 `efb.service` 与管理器不要同时运行。如果原服务可以登录而管理器失败，应对照排查流程差异，不能只凭 1203 判定账号被限制。

## 归档错误排查

v0.3.12 起，归档失败会显示阶段、异常类型和分类原因，例如“写入数据库 / OperationalError：数据库忙”或“数据库结构不完整”，不再把所有错误统一归因于磁盘与权限。具体提示同时保留在运行日志；后续写入成功会自动清除页面上的错误提示。归档失败不会主动阻止 EFB 转发，但失败期间的归档不保证自动补回。

出现问题时先查看更新后的完整提示，确认管理器和其 EFB 子进程都已重启、使用同一版本；不要直接删除消息库或放宽目录权限。检查实际 `--state-dir`、服务运行用户，以及是否有多个实例操作同一消息库。
